# Deploying Occavie

**Status:** the steps below are prepared and the production profile was exercised locally (see "What was verified").
Nothing has been deployed to a live host from this repository yet, so no live URL is claimed.

## Which host?

| Option | Verdict |
|---|---|
| **Render (Docker web service)** | **Recommended.** Runs the Spring Boot jar as a long-lived process, which is what Occavie is. |
| Vercel | **Not recommended / not tested.** Vercel is built around static sites and serverless functions. A Spring Boot app is a long-running Java server with in-memory HTTP sessions, an in-process scheduler (reminders, email outbox) and local state. Vercel's container runtime (as described in public search summaries; I could not open vercel.com from the build sandbox to confirm) is a beta, stateless, scale-to-zero model, which breaks sessions and background jobs. A static deploy of the HTML templates would not work at all, because the pages are rendered by the server. |

The backend framework is unchanged (Spring Boot + Thymeleaf + MongoDB).

## Architecture notes that affect hosting

* **One instance only.** HTTP sessions live in Tomcat memory. Scaling to 2+ instances logs users out at random. Use Render's single-instance plan (or add Spring Session + Mongo/Redis first).
* **Use a paid instance for a real demo.** Free instances spin down when idle, which drops sessions and delays the first request.
* **Images are stored in MongoDB**, so there is no disk to lose. Database size, not disk size, is the limit.
* **Scheduled work** (email outbox, reminders, waitlist offer expiry) runs in-process every `OCCAVIE_JOBS_POLL_MS` (60 s). If the instance sleeps, jobs pause; an external scheduler can call `POST /internal/jobs/run` with header `X-Jobs-Token: <OCCAVIE_JOBS_TOKEN>`.
* **Payments are simulated.** Amounts are demo values, never real revenue.

## 1. Push to GitHub

```bash
git push -u origin main
```

(Work for this release is on branch `claude/gracious-planck-2724b7`; merge it into `main` first via a pull request.)

## 2. MongoDB Atlas

1. Create a free M0 cluster and a database user (a strong password, `readWrite` on the `eventflow` database only).
2. **Network Access:** Render's outbound IPs change, so for a demo add `0.0.0.0/0` and rely on the strong database password; for production use Render's published outbound IP ranges or a private network instead.
3. Copy the `mongodb+srv://…` connection string and replace `<password>`. Include the database name: `…mongodb.net/eventflow`.

## 3. Create the Render service

1. Render dashboard → **New → Blueprint** → choose this repository. It reads `render.yaml`.
   (Alternative: **New → Web Service → Docker**, health check path `/readyz`.)
2. Fill the prompted values:

| Variable | Value |
|---|---|
| `MONGODB_URI` | your Atlas string |
| `OCCAVIE_PUBLIC_URL` | `https://<service>.onrender.com` (no trailing slash; must be https) |
| `OCCAVIE_BOOTSTRAP_ADMIN_EMAIL` / `_PASSWORD` | your real admin login (8+ chars with upper, lower, digit and symbol; longer is better) |
| `OCCAVIE_REMEMBER_KEY`, `OCCAVIE_TICKET_SECRET`, `OCCAVIE_JOBS_TOKEN` | generated by the blueprint |
| `OCCAVIE_SAMPLE_EVENTS` | `true` to fill an empty database with sample events (does nothing if events already exist) |
| `OCCAVIE_CONTACT_EMAIL`, `OCCAVIE_CONTACT_WHATSAPP` | shown on Contact page and footer (optional) |
| `OCCAVIE_EMAIL_PROVIDER=resend`, `RESEND_API_KEY`, `OCCAVIE_EMAIL_FROM` | optional; required for password-reset emails |

3. Deploy. The app **refuses to start** with a clear message if a secret is missing, weak, shared, or the public URL is not https. `PORT` is injected by Render.
4. After the first successful start, **delete `OCCAVIE_BOOTSTRAP_ADMIN_PASSWORD`**. On that first start the three public demo accounts (`*@eventflow.com`) are disabled automatically once a real admin exists.

## 4. Logs and checks

* Render → service → **Logs**. Look for `Started EventflowApplication` and `Created the first administrator account`.
* `https://<service>/healthz` → `{"status":"UP"}` (process alive). `https://<service>/readyz` → also pings MongoDB (HTTP 503 if the database is unreachable).
* Verify MongoDB: Atlas → Browse Collections → `eventflow` should contain `users`, `events`, … after the first request. Log in as the bootstrap admin and create an event, then confirm it appears in `events`.

## 5. Live verification checklist (tick each on the real URL)

- [ ] Homepage loads, logo and fonts render, no mixed-content warnings (browser console).
- [ ] `/events` lists events; search and filters work.
- [ ] Event details page opens; share preview (Open Graph) shows title and image.
- [ ] Register a new participant; log in and out.
- [ ] Demo accounts (`admin@eventflow.com`, …) are **rejected**.
- [ ] Bootstrap admin can log in; Admin dashboard loads.
- [ ] Organizer: create/publish an event (wizard); event shows publicly (or in Approvals if enabled).
- [ ] Participant: free booking works; PDF ticket downloads and shows a QR code.
- [ ] Simulated paid booking works and is labelled as a demo payment.
- [ ] Organizer check-in page verifies the QR; a second scan reports "already checked in".
- [ ] Role protection: participant opening `/admin/dashboard` or `/organizer/events` gets the access-denied page.
- [ ] CSV export downloads from an event's participants page (organizer only).
- [ ] Cancel a free registration; waitlist promotion works when a seat frees up.
- [ ] Password reset email arrives (only if email is configured).
- [ ] `/robots.txt`, `/sitemap.xml`, `/healthz`, `/readyz` respond; an unknown URL shows the custom 404 page.
- [ ] Cookies are `Secure; HttpOnly; SameSite=Lax` (DevTools → Application → Cookies).

## What was verified (locally, not on Render)

* Boot with `SPRING_PROFILES_ACTIVE=prod`: refuses unsafe secrets; boots with safe ones; bootstrap admin created; demo-admin login rejected; real admin login works; session cookie is `Secure; HttpOnly; SameSite=Lax`; `/healthz` and `/readyz` respond.
* **Not verified:** the Docker image build (no Docker daemon in the build sandbox), a real MongoDB Atlas connection, Render itself, real email delivery, and multi-document transactions (Atlas supports them; the local in-memory test database does not).

## Vercel (only if you still want to try)

Untested and unsupported here. A workable path would need: a Docker/container deployment option on your Vercel plan, `SPRING_PROFILES_ACTIVE=prod`, sessions moved out of memory (Spring Session), the in-process scheduler replaced by calls to `/internal/jobs/run`, and a fixed-IP or open Atlas allowlist. Check Vercel's current docs before investing time.
